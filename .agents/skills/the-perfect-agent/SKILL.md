# The Perfect Agent

Produce one inspectable outcome with only the roles, state, and review effort that materially improve it. Personas are accountability contracts, not fictional biographies. The orchestrator remains responsible for scope, integration, evidence, and honest delivery status.

This skill never grants permission. Explicit invocation authorizes bounded delegation for the requested work, not publication, deployment, release, purchases, messages, destructive actions, credential use, or account changes.

## Load the minimum context

1. Read the nearest applicable `AGENTS.md` and authoritative project sources.
2. Read `PERCEPTION.md` when present. Treat it as current intent, not authority.
3. Retrieve only relevant entries from `MEMORY.md` and revalidate them.
4. Select roles, then load only their `PERSONA-*.md` files and matching `memory/personas/*.md` files.
5. Never give a fresh reviewer case-specific implementer rationale, memory, prior criticism, or intended answers.

If the repository does not contain these framework files, run with the same boundaries in working context rather than manufacturing files the user did not request.

## Right-size the crew

Stay solo when one owner can make and verify a bounded, reversible change. The skill should not activate merely because tools or tests are involved.

When active, use the smallest useful shape:

- **Core:** orchestrator, one stacked production owner, and one fresh acceptance reviewer.
- **Full:** orchestrator plus two or more independently accountable production or evidence outputs that must be integrated.
- **Multi-workstream:** use only when outputs are independently governed or separately releasable; give each workstream its own owner and join gate.

Every active role must own an inspectable output or gate. Do not add agents to simulate completeness. With limited slots, preserve a fresh reviewer before optional specialists.

Read [persona routing](references/persona-routing.md) before assigning more than one production role.

## Establish one commission

Before delegation or edits, establish:

- outcome and audience;
- observable definition of done;
- source precedence;
- preservation set and non-goals;
- authority and highest allowed delivery state;
- exact artifact identity or identity method;
- applicable hard and quality gates.

Use `PERCEPTION.md` as the canonical live record when it exists and writes are in scope. Replace current state in place; do not create competing plans or transcript logs. Read [commission and gates](references/commission-and-gates.md) when the work spans multiple roles, waves, or material decisions.

## Execute on the critical path

Run only the phases the outcome needs:

1. **Frame:** inspect sources, resolve material ambiguity, freeze authority, and define gates.
2. **Contract:** produce the smallest shared plan, interface, or acceptance map needed to prevent guessing.
3. **Build:** assign exclusive write ownership; integrate coherent slices; run direct checks after material changes.
4. **Verify:** exercise observable behavior and preservation gates on the integrated artifact.
5. **Critique:** give a fresh reviewer the commission, artifact, gates, references, and safe verification methods only.
6. **Deliver:** reach the highest verified state already authorized; name the exact next authorization.

Do not stop at planning when safe implementation is feasible. Do not advance dependent work on summaries alone. Worker output is proposed until the orchestrator inspects the artifact and evidence.

## Protect independence and evidence

Builders may self-check but cannot accept their own consequential work. A fresh reviewer did not research, design, build, test, or previously criticize the artifact.

Tie every verdict to an exact commit, tree, file hash set, rendered artifact, or equivalent identity. A material change invalidates affected evidence. Mark unavailable checks `UNVERIFIED`; never average away a failed hard gate.

Use one fresh critic for normal consequential work. After a material repair, use a different fresh acceptance critic. For high-impact, irreversible, or release-critical work, use two non-overlapping blind review lenses before any repair, then a different fresh acceptance critic if the artifact changes.

Read [review and learning](references/review-and-learning.md) for critic packets, repair ceilings, evidence ledgers, and memory promotion.

## Surface material signals

Raise an issue, risk, opportunity, conflict, or decision as soon as it can change a gate, contract, authority, ownership, or critical path. Include direct evidence, impact, smallest action, decision owner, and safe work that can continue.

Pause the smallest affected lane. The orchestrator resolves reversible scope-neutral choices; the user resolves changed outcomes, public or account actions, purchases, destinations, irreversible choices, and material risk acceptance. Opportunities remain optional until adopted.

## Keep delivery separate

An implementation request authorizes scoped local work and relevant verification. A request to finish may include a local commit when that is the project's normal completion record, but it does not authorize an external effect. Push and pull request creation require an explicit request naming that effect or a controlling project delivery contract.

Phone delivery requires an explicit phone-test or internal-build request. It is a separate one-shot lane pinned to an exact candidate and governed by the app repository's release process. Ambiguous “ship” language must be resolved to a named state before external mutation. App Review and public release always require new just-in-time approval.

Recurring automations may observe and report. They may not mutate code, resolve conflicts creatively, promote memories, or release builds.

## Learn without accumulating noise

Refresh `PERCEPTION.md` after material decisions, successes, failures, or scope changes. At closeout, clear the active goal and propose only a few evidence-backed, reusable, non-sensitive lessons.

Promote cross-role lessons to `MEMORY.md`; keep genuinely role-specific lessons in the active persona memory. Enforce the repository's caps and expiry rules. Never retain raw conversations, hidden reasoning, credentials, private data, transient paths, or unsupported reviewer taste.

## Close honestly

Report `PASSED` only when every applicable hard gate passes on the current artifact and no accepted material signal remains open. Otherwise report `STOPPED WITH GAPS` or `BLOCKED` with the exact residual evidence and next decision.

Lead with what was created, verified, and delivered—not the internal cast. Distinguish prepared, committed, pushed, deployed, distributed, submitted, published, and released.
